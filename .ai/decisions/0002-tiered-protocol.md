# 0002 - README First 按风险分级执行

## 背景

README First v1 对所有任务执行同一套 10 步完整协议:每次任务必读 AGENTS.md 全文、根 README、路径 README、核对 README-代码一致性,并用 11 字段模板记录变更。这一协议在降低不确定性上有效,但对低风险任务(如改错别字、局部样式、单文件小修)产生了不成比例的流程成本。经验表明,低风险任务的不确定性上限本身就很低,完整协议并不能进一步降低它,只会消耗上下文窗口和维护耐心。

同时,日常任务中被"卸下"的系统性维护——文档漂移巡检、变更记录压缩、重复经验沉淀——需要有一个明确的执行者和时机,否则会逐渐积累成新的债务。

## 决策

引入 L0 / L1 / L2 三级任务分级,并配套差异化的读取范围、任务契约、记录深度和输出要求:

- **L0(轻量)**:只读或 1–2 个文件内的显而易见修改,不触及接口、数据、配置、权限、安全,不改变目录职责。成本:读最近一级 README、commit、一句话回复,不写 changes。
- **L1(标准)**:单个模块内的常规功能与修复,不触及公共接口。使用简版三项契约,短模板记录。
- **L2(高影响)**:公共 API、共享类型、数据结构、配置、权限、安全、删除文件、跨模块、架构调整,或存在中高风险/不可逆不确定性。使用完整八项契约,完整模板记录,必须逐条核对 README 更新触发条件。

两条元规则保证安全:

1. 定级拿不准 → 按更高级别执行。
2. 执行中发现命中 L2 特征或中高风险不确定性 → 立即升级。

系统性维护工作从日常任务剥离,集中到 `readme-first-maintainer` 技能定期批量完成:健康巡检、记忆压缩、知识沉淀、协议校准。

考虑过但放弃的替代方案:

- **保持 v1 统一流程**:简单,但低风险任务成本过高,实践中会导致记录敷衍或抵触。
- **完全取消记录**:不可接受,会丢失变更原因和假设。
- **由每个 Agent 自行决定是否轻量**:缺乏一致性和可审计性,容易出现为规避流程而低报级别。

## 影响

- 根 `AGENTS.md`、根 `README.md` 必须按 v2 重写。
- `skills/readme-first-builder/` 升级为 v2(离线优先、P0 渐进覆盖),并新增 `skills/readme-first-maintainer/`。
- `.ai/architecture/` 中涉及 changes 契约、skill 边界、读取方向的文件需要同步更新。
- 所有后续任务必须先读 `AGENTS.md` 第 0 节最小闭环,再按级别执行。
- 禁止为规避流程而低报任务级别。

## 非目标

- 本决策不降低对高风险任务的审查要求;L2 仍执行完整协议。
- 本决策不取消 `.ai/changes/` 和 `.ai/decisions/` 的记录价值,只是按级别缩放记录深度。
- 本决策不意味着日常任务完全不做 README-代码核对,而是只核对与本次修改直接相关的声明;系统性核对交给 maintainer。
