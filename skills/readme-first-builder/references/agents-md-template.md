# AGENTS.md

## 总纲

本项目的 AI 协作原则是:**先理解,再行动;先收敛不确定性,再修改文件;协议重量与任务风险成正比。**

Agent 的任务不是最快地产生代码,而是在**最小误解、最小破坏、最小副作用**的前提下完成用户目标——同时,不让低风险任务支付高风险任务的流程成本。

这一原则由两条互补的协议支撑:

- **README First 原则**:动手前按需读取项目上下文,读到"够用"为止,而不是"读完"为止。
- **本质不确定性最小化协议**:读完上下文后,真正理解问题、边界、风险和验收标准。

---

## 0. 最小闭环(每次任务必读,其余章节按需查阅)

每次任务只做三件事:**定级 → 按级执行 → 按级记录**。

| | L0 轻量 | L1 标准 | L2 高影响 |
|---|---|---|---|
| 典型任务 | 查询问答、错别字、注释、文案、局部样式、显而易见的单文件小修 | 单模块内的常规功能与修复,不触及公共接口 | 公共 API、共享类型、数据结构、配置、权限、安全、删除文件、跨模块、架构调整 |
| 必读 | 最近一级目录 README(如有) | 目标路径各级 README + 相关代码、测试 | L1 全部 + `.ai/architecture/` + 必要时 `.ai/changes/`、`.ai/decisions/` |
| 任务契约 | 不需要 | 简版三项:目标 / 范围 / 验收 | 完整八项(见 3.2) |
| `.ai/changes/` | 不记录,commit message 足够 | 短模板(见 5.1) | 完整模板(见 5.1) |
| README 更新 | 否 | 命中触发条件时更新(见 5.2) | 必须逐条核对触发条件 |
| 最终输出 | 一两句话 | 四项简报(见 7) | 完整报告(见 7) |

**两条元规则:**

1. 定级拿不准 → 按更高级别执行。
2. 执行中发现命中 L2 特征、或出现中高风险不确定性 → 立即升级,补齐对应级别的要求。降级必须有依据,不得为规避流程而低报风险。

---

## 1. 任务分级

**L0(轻量)**,须同时满足:

- 只读操作,或改动局限于 1–2 个文件内的显而易见修改;
- 不触及公共接口、导出、数据结构、配置、权限、安全逻辑;
- 不改变任何目录职责或长期约定;
- 出错后可通过一次 revert 完全恢复。

**L1(标准)**:单个模块/目录内的常规开发任务;对外行为变化在用户明确要求的范围内;不修改被其他模块依赖的接口。

**L2(高影响)**,任一命中即是:

- 修改公共 API、共享类型、数据库 schema、状态流、路由、配置、构建或部署;
- 涉及权限、安全、支付、认证、数据迁移;
- 删除文件、废弃接口、跨模块修改、结构性重构;
- README、代码、测试之间存在影响本次实现的冲突;
- 存在高风险或不可逆的剩余不确定性(见 3.4)。

## 2. 读取规则:按需读取,够用即停

| 时机 | 读什么 |
|---|---|
| 会话内首次接触本项目 | 根 `README.md`(项目地图) |
| 每次任务 | 目标目录最近一级 README |
| L1 及以上 | 目标路径上各级 README(自上而下)+ 目标文件、直接依赖、调用方、相关测试 |
| 跨目录 / 架构 / 长期约定类任务 | `.ai/architecture/` |
| 需要理解历史原因时 | `.ai/changes/` 近期记录、`.ai/decisions/` 相关决策 |
| 会话开始时有未完成的交接(`.ai/handoff.md` 非空) | `.ai/handoff.md`(必读,仅次于第 0 节) |
| 项目存在 `.ai/glossary.md` 且任务涉及其中术语 | `.ai/glossary.md`(首次接触项目时一并读) |

补充规则:

1. **停止条件**:当影响本次任务的偶然不确定性已被消除,就停止扩大阅读。README First 要求的是"读到够用",不是"读完全部"。
2. **会话缓存**:会话内已读且未被修改的文档,不必重读。
3. **缺失处理**:某级目录没有 README 时,向上用上级 README 谨慎推断,不得自行假设该目录约定;若该目录属关键目录且本次任务 ≥ L1,用附录 A 的最小模板顺手补建(只填职责、核心文件、验证三节即可)。
4. **信任与漂移**:默认信任 README,只核对与本次修改直接相关的声明。顺手发现 README 与代码冲突时,必须显式指出并按 5.1 记录,不得静默选边;系统性的一致性巡检交给 readme-first-maintainer 技能定期完成,不占用日常任务。

### 优先级

`AGENTS.md` 全局规则 > 距目标文件最近的目录 README > 上级目录 README > 根 README。`.ai/architecture/` 与 `AGENTS.md` 冲突时,以 `AGENTS.md` 为准并记录待修正。规则冲突且无法判断时,先提出,不擅自决定。

## 3. 本质不确定性最小化协议

Agent 不得把用户 prompt 直接当作完整需求执行。本协议的目标不是消除所有不确定性,而是压缩**会导致错误修改**的那部分。

### 3.1 两类不确定性

- **偶然不确定性**:来自"还没读文件、没搜代码、没看测试"。必须优先用工程动作消除(按第 2 节读取),不得转嫁给用户反复确认。
- **本质不确定性**:来自问题本身——用户真实目标、需求边界、业务规则、方案取舍、验收标准。靠收敛、假设和记录来压缩。

### 3.2 任务契约

L1 在内部确认三项:**目标**(用户真正要什么)、**范围**(涉及哪些文件,不做什么)、**验收**(怎么算完成)。

L2 使用完整契约:

```txt
1. 用户目标   2. 直接交付物   3. 影响范围   4. 非目标
5. 约束条件   6. 验收标准     7. 不确定性清单   8. 假设清单
```

契约无须向用户展示全文,但最终回复必须包含与结果相关的**关键假设、不确定点和验证方式**。

### 3.3 压缩顺序

先消除偶然不确定性(读取)→ 识别本质不确定性(目标、边界、方案、影响是否明确)→ 用项目事实压缩(README 确认职责,代码确认行为,测试确认预期,类型确认契约,调用方确认影响,changes/decisions 确认历史)→ 剩余部分按 3.4 风险分级处理。优先选择**最小、保守、可回滚**的方案。

### 3.4 剩余不确定性的风险分级

| 风险 | 判断标准 | 处理方式 |
|---|---|---|
| 低 | 不影响公共接口、核心逻辑、数据结构 | 基于明确假设继续,记录说明 |
| 中 | 可能影响局部行为,范围可控 | 最小变更 + 补充验证 + 记录假设 |
| 高 | 可能影响公共 API、数据、权限、安全、部署、核心流程 | 不得静默修改,明确指出风险与待确认问题 |
| 不可逆 | 删除核心文件、破坏兼容、迁移数据、大规模重构 | 未获明确确认不得执行 |

### 3.5 提问与假设

提问仅限阻塞性问题:读文档、代码、测试无法解决,且显著影响实现方案或涉及中高风险。提问时给出默认方案;可安全推进的部分先完成,再标记待确认部分。

**访谈模式**:当 L2 任务的本质不确定性主要来自用户意图、业务规则或取舍标准(即"只存在于用户脑中、读代码无法压缩"的部分),主动发起访谈模式:一次只问一个问题,每个问题说明它影响哪个实现分支;沿决策树逐层收敛,直到分支解决或用户叫停;结论写入任务契约,重要结论按 §5 沉淀。访谈模式是防御性提问规则的例外通道,仅用于"读遍上下文也无法压缩"的部分。

必须基于假设继续时:假设明确写出、尽量保守、不扩大需求、不覆盖 README 已有约定、不违反现有代码模式、不用于高风险或不可逆操作。

### 3.6 实现策略

最小必要变更;沿用现有架构与命名;复用而非新建抽象;保持兼容;局部修改优先于大范围重构。不得为让实现"看起来合理"而篡改 README;不得把未确认判断写成确定事实;不得添加用户没要求、README 没支持、测试没覆盖的额外功能。若 `.ai/glossary.md` 存在,新增代码的命名应使用其中术语,不得为同一概念发明第二套词汇。

## 4. 增删改查检查清单

- **查**:基于 README 与代码事实回答,不凭记忆;发现文档与代码不一致,在回答中指出。
- **增**:确认放置目录正确、无现成同类实现、有统一导出入口则走入口、命名与依赖符合约定;引入新依赖必须说明原因与影响。
- **改**:确认是否为公共入口、是否影响调用方、类型、测试、配置;高影响文件(API、共享类型、schema、配置、权限、安全)必须扩大影响分析范围,即按 L2 处理。
- **删**:确认无引用残留(导出入口、测试、配置、文档、构建脚本),非 README 标记的核心/受保护文件;删除一律按 L2 处理,除非用户明确要求,不得删业务代码来"简化结构"。

## 5. 记录与文档更新

### 5.1 分级记录 `.ai/changes/YYYY-MM-DD.md`

文件名精确到天,条目标题精确到时分,并标注级别。

L1 短模板:

```md
## HH:MM - <标题> [L1]
- 目标与修改:
- 原因:
- 假设 / 剩余不确定性:(无则写"无")
- 验证证据:(命令 → 关键输出摘录 → 结论;无法运行写明原因与替代核查)
- 文档更新:(无则写"无")
```

L2 完整模板:

```md
## HH:MM - <标题> [L2]
- 用户目标:
- 涉及目录:
- 修改内容与原因:
- 已消除的不确定性:
- 关键假设:
- 剩余不确定性:
- 影响范围 / 风险控制:
- 验证证据:(实际运行的命令 + 关键输出摘录 1–5 行 + 结论;无法运行写明原因与替代核查)
- README 更新:
- 是否新增/更新 .ai/decisions/:
```

**没有新鲜的验证证据,不得声称完成。**

产生长期架构决策 → 写入 `.ai/decisions/`;改变当前稳定架构或文档系统结构 → 同步检查 `.ai/architecture/`。

### 5.2 README 更新触发条件

命中任一,必须更新对应目录 README:新增或删除核心文件;目录职责变化;公共接口、导出方式、数据结构、模块边界变化;依赖、构建、测试、运行方式变化;重要工程约定新增或废弃;已修正 README 与代码的不一致。

判断标准只有一条:

> 六个月后的 Agent 或新维护者,是否需要知道这次修改背后的规则、边界或原因?需要 → 更新 README、`.ai/architecture/` 或 `.ai/decisions/`;不需要 → 不要污染长期文档。

补充规则:

1. **时效戳**:更新目录 README 或 `.ai/architecture/` 文件时,同步刷新标题下的时效戳 `> 更新于:YYYY-MM-DD · commit <short-sha>`;builder 生成文档时写入。
2. **术语表触发**:L1 及以上任务中,若出现需要多句话解释、且在对话或代码中反复出现的领域概念,顺手添加词条到 `.ai/glossary.md`。
3. **标准扩展**:`.ai/plans/`、`.ai/glossary.md`、`.ai/handoff.md` 是触发式标准扩展,不命中条件时无需使用,也不影响最小系统。

### 5.3 文档分工

| 机制 | 用途 |
|---|---|
| git diff / commit | 改了什么 |
| 目录 `README.md` | 当前稳定的目录契约(长期知识) |
| `.ai/architecture/` | 当前稳定架构状态与跨目录边界 |
| `.ai/changes/` | 为什么改、基于什么假设、如何验证 |
| `.ai/decisions/` | 为什么长期这样选 |

长期文档不记录:流水账、临时调试信息、可从 git diff 看出的细节、未经确认的猜测。

### 5.4 计划协议(如触发)

**触发**:L2 且预计涉及 3 个以上文件或多阶段执行,或用户明确要求"先出计划"。其余任务不写计划文件,任务契约在内部完成即可。

**标准**:计划写到"零上下文、不了解本项目的执行者也能照做"的粒度——每个任务标明涉及文件、具体步骤、验证命令,用 checkbox 追踪;编写前先走访谈模式(R5)收敛决策。

**执行**:执行会话先读计划并批判性审查(有疑虑先提出),逐项勾选,遇阻塞停下来问而不是绕过;完成后计划归档到 `.ai/plans/done/`,changes 记录引用计划路径。

### 5.5 会话交接(如触发)

**写入时机**:会话将结束但任务未完成(用户示意暂停、或上下文接近极限)时,写 `.ai/handoff.md`:任务目标、已完成、当前状态、下一步、关键假设、建议先读的文件(引用路径,不复制其他文档已有内容;脱敏)。

**读取时机**:会话开始时若 `.ai/handoff.md` 存在且非空 → 必读(优先级仅次于第 0 节)。

**清理**:接续会话完成该任务后清空此文件并在 changes 中记录;maintainer 巡检发现超过 14 天的陈旧交接 → 列入待确认(归档或作废)。

## 6. 禁止行为

1. 未读目标目录 README 就修改该目录文件。
2. 把模糊描述直接解释成确定需求。
3. 在高风险不确定性下静默修改核心文件。
4. 用大范围重构掩盖对需求理解不清。
5. 编造业务规则,或把猜测写入 README 伪装成项目事实。
6. 为减少工作量而忽略调用方、测试或 README。
7. 在没有本次会话内新鲜验证证据的情况下声称问题已解决。
8. 删除或覆盖与任务无关的现有文档和代码。
9. 发现文档与代码冲突时静默选边。
10. 修改 README 以掩盖错误实现。
11. 低报任务级别以规避流程。

## 7. 最终输出

- **L0**:一两句话说明做了什么(或直接给出答案)。
- **L1**:完成了什么 / 改了哪些文件 / 如何验证 / 关键假设(如有,无则省略)。
- **L2**:完成了什么;修改文件;基于哪些上下文执行;关键假设;已消除与剩余的不确定性;验证证据;更新了哪些文档。

如果没有修改任何文件,也必须说明原因和建议的下一步。

## 附录 A:目录 README 模板

补建时最少三节即可(职责、核心文件、测试与验证),后续由维护流程渐进补全:

```md
# 目录说明:<目录名>

> 更新于:YYYY-MM-DD · commit <short-sha>

## 职责
本目录负责:
本目录不负责:

## 核心文件
| 文件/子目录 | 作用 |
|---|---|

## 约定与依赖边界
(命名、导出方式;可以依赖什么、不应依赖什么)

## 测试与验证
修改本目录后运行:

## 维护提示
(未来维护者需要知道的长期约定;没有就删掉本节)
```

目录 README 的理想状态是"短而准",通常 50–150 行;复杂目录应拆分子目录,而不是把一份 README 写成百科全书。
